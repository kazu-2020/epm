# ADR の書き方

ADR は決定の経緯の記録であり、正はコードである。試作段階の ADR は後続の作業を拘束する制約ではなく、その時点の判断である。コードと ADR が食い違う場合はコードを正とする。

目的は、半年後の開発者や新規の参加者が、1つの ADR だけを読んで「何を、なぜ決めたか」を理解できることである。当時の会話や他の ADR を読まなくても理解できる状態を基準にする。

## ADR を書く条件

次の3条件がそろう決定だけを ADR にする。1つでも欠ける場合は、コミットログや PR の説明に書く。

1. 変更のコストが大きい。
2. 文脈を知らない読者には意外である。
3. 実際に代替案があり、理由をもって1つを選択した。

## 手順

1. `docs/adr/` の最大番号に1を加えて番号を決める。ファイル名は `NNNN-<決定を表す英語の slug>.md`。
2. [template.md](template.md) を複製し、全見出しを埋める。該当のない任意の見出しは削除する。
3. 下記の規則で点検する。
4. `pnpm lint:ja` で校正する。

## 見出しと書く内容

| 見出し | 必須 | 書く内容 |
| --- | --- | --- |
| タイトル | 必須 | 決定を1文で書く。例: 「SUM はグループのセルを座標の小さい順に足す」。 |
| 冒頭の属性 | 必須 | 決定日、状態、関連する issue と PR。 |
| 背景 | 必須 | 何が問題だったか。読者が知らない前提、制約、用語をここで説明する。 |
| 決定事項 | 必須 | 何を決めたか。範囲外のことも明記する。 |
| 理由 | 必須 | なぜその案を選択したか。比較の根拠 (計測値、検証結果、文献) を示す。 |
| 不採用の案 | 必須 | 案ごとに、内容と不採用の理由を書く。 |
| 影響 | 必須 | この決定で困難になること、受け入れたトレードオフ、見直す条件。 |
| 未決事項 | 任意 | この決定で解決しなかった問題と、その issue。 |

状態は「採用」「ADR-NNNN で置き換え」のどちらかである。

## 規則

- 1つの ADR に1つの決定を書く。決定が複数ある場合は ADR を分割する。
- 自己完結させる。依存する決定は1文で要約してリンクする。「ADR-0006 を参照」だけで済ませない。
- 用語は GLOSSARY.md の用語を使い、初出でリンクする。GLOSSARY.md にない用語は背景で定義する。
- 略語は初出で正式名称を書く。スレッド内の呼び名 (「方式 A」など) を書かない。リポジトリだけで意味が分かる言葉で書く。
- 型名、crate 名、ライブラリ名は英語のまま書く。変更されやすい関数名や行番号には依存しない。
- 運用手順、検証の詳細、ベンチマークの生データは ADR に入れない。別の文書やコードに置き、ADR からはリンクと要点だけを書く。
- 改訂履歴を書かない (git で追跡できる)。
- 本文は「である」調。和語を避け、熟語とカタカナ語で書く。

## 決定を変更するとき

古い ADR の本文は書き換えない。当時の判断の記録だからである。新しい ADR を作り、背景に古い ADR の決定と変更の理由を書く。古い ADR は冒頭の状態だけを「ADR-NNNN で置き換え」に更新する。

誤字や壊れたリンクの修正は本文を直してよい。
