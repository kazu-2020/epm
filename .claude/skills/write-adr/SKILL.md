# ADR の書き方

ADR は決定の経緯の記録であり、正はコードである。試作段階の ADR は後続の作業を拘束する制約ではなく、その時点の判断である。コードと ADR が食い違う場合はコードを正とする。

目的は、半年後の開発者や新規の参加者が、1つの ADR だけを読んで「何を、なぜ決めたか」を理解できることである。当時の会話や他の ADR を読まなくても理解できる状態を基準にする。

書式は Michael Nygard の原典の項目 (Context、Decision、Status、Consequences) を基本にする。これに Alternatives Considered を加える。

## ADR を書く条件

次の3条件がそろう決定だけを ADR にする。1つでも欠ける場合は、コミットログや PR の説明に書く。

1. 変更のコストが大きい。
2. 文脈を知らない読者には意外である。
3. 実際に代替案があり、理由をもって1つを選択した。

数値の調整 (期限、回数、閾値) は、方式の決定に付随する場合を除いて ADR にしない。

## 手順

1. `docs/adr/` の最大番号に1を加えて番号を決める。ファイル名は `NNNN-<決定を表す英語の slug>.md`。
2. [template.md](template.md) を複製し、全項目を埋める。
3. 下記の規則で点検する。分量が目安を超えた場合は分割か詳細の移動を検討する。
4. 決定が現れるコードの Why not コメントに ADR の番号を書く (例: `(ADR 0001)`)。
5. `pnpm lint:ja` で校正する。

## 項目と書く内容

| 項目 | 書く内容 |
| --- | --- |
| タイトル | 決定を1文で書く。例: 「SUM はグループのセルを座標の小さい順に足す」。 |
| Status | `Accepted`、`Deprecated` (決定自体を廃止した)、`Split into ADR-NNNN, ADR-MMMM` のいずれか。 |
| Date / Updated | 最初の決定日と、最後に書き換えた日。書き換えていない場合は Updated を削除する。 |
| Related | 決定の議論が残る issue と PR の番号。本文には issue や PR の番号を書かず、ここに集める。 |
| 要約 | 見出しなしの1段落。「〜の状況で、〜の問題に対し、〜を採用し、〜を不採用とした。〜を達成し、〜を受け入れた。」の順で書く (Y-statement 形式)。 |
| Context | 何が問題だったか。決定しない場合に何が起きるか。読者が知らない前提、制約、用語。 |
| Decision | 何を決めたか、なぜその案か。末尾に「範囲外」と「検証」を書く。 |
| Alternatives Considered | 案ごとに、内容と不採用の理由を書く。 |
| Consequences | この決定で困難になること、受け入れたトレードオフ、未解決の部分。末尾に「見直す条件」を書く。 |

### 根拠の種類

Decision の各根拠の末尾に、次の記号を付ける。読者はこの記号で、どの規則を安全に変更できるかを判断する。

- 【検査】: モデル検査や性質の試験で、規則を除外すると違反することを確認した。
- 【実測】: 計測の結果がある。
- 【推定】: 実測値からの計算である。
- 【未検証】: 推論だけである。

### 範囲外、未解決、見直す条件

- 範囲外 (Decision の末尾): この ADR が扱わない事項。別の決定の対象である。
- 未解決 (Consequences): この ADR が扱う問題のうち、まだ解決していない部分と、その issue。
- 見直す条件 (Consequences の末尾): どの状態になったら見直すか。見直す条件はここだけに書く。

### 検証

この決定を守っている試験、型、モデルのパスを書く。読者がコードへ到達する経路である。プロトコルや状態遷移の決定では、守る不変条件も書く。

## 規則

### ADR に入れないもの

判定の基準: 実現方式を別の方式に置き換えたとき、ADR の本文を書き換える必要があるなら、その記述は ADR に属さない。

- 実装の詳細 (SQL の条件、関数の構造、手順の順序)。コードと PR の説明に置く。
- 運用手順、検証の詳細な結果、ベンチマークの生データ。PR の説明、試験コード、モデルの README に置き、ADR からはリンクと要点だけを書く。
- 移行計画、進捗、作業の TODO。issue にする。
- 改訂履歴。git で追跡できる。

### 粒度と分量

- 1つの ADR に1つの決定を書く。片方だけを覆せる決定は別の ADR に分ける。相互に前提とし、一緒にしか変更できない決定群は1つの ADR にしてよい。
- 本文の目安は2,000字以内である。超える場合は、分割か詳細の移動を検討する。
- 分割した ADR は、それぞれ Context に共通の前提を1段落で要約する。共通の前提が長い場合は、前提を GLOSSARY.md に移すか、前提そのものを1つの ADR にしてリンクする。

### 自己完結

- 依存する決定は1文で要約してリンクする。「ADR-0006 を参照」だけで済ませない。
- 作成されていない ADR の番号を参照しない。未決の事項は issue を参照する。
- 前提には出典 (ADR、issue、PR) を書く。出典がない前提は、その旨を明記する。
- 用語は GLOSSARY.md の用語を使い、初出でリンクする。GLOSSARY.md にない用語は Context で定義する。
- 略語は初出で正式名称を書く。スレッド内の呼び名 (「方式 A」など) を書かない。他のリポジトリや過去の試作を参照する場合は、内容を本文で説明する。

### コードとの関係

- 型名、crate 名、ライブラリ名は英語のまま書く。変更されやすい関数名や行番号には依存しない。
- 暫定値や定数は方針 (例: 「前回の起動時間の2倍」) だけを書き、値はコードの定数のパスを示す。ADR に値を書くと、コードの変更で乖離する。
- 決定が現れるコードには、Why not コメントに ADR の番号を書く。エージェントがコードから ADR へ到達する主な経路である。

### 文体

- 項目名は英語、本文は日本語の「である」調。和語を避け、熟語とカタカナ語で書く。

## 決定を変更するとき

同じ ADR を書き換える。本文は常に現在の決定だけを示し、履歴は git で追跡する。置き換えの ADR は作らない。古い決定が残っていると、エージェントが古い決定に従い続けるためである。

1. Decision、Consequences などを現在の決定に書き換える。
2. 覆した旧案を Alternatives Considered に移し、不採用にした理由を書く。git の履歴を読まなくても、なぜ変えたかが分かるようにする。
3. Updated を書き換えた日にする。
4. タイトルが変わる場合はファイル名の slug も変更し、リポジトリ内のリンクとコードのコメントを直す。番号は変えない。

決定自体を廃止した場合は Status を `Deprecated` にし、Context に廃止の理由を書く。

1つの ADR を複数に分ける場合だけ、新しい番号を作る。元の ADR は Status を `Split into ADR-NNNN, ADR-MMMM` にし、本文を分割後の ADR へのリンクだけにする。
