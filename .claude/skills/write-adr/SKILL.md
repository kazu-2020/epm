# ADR の書き方

ADR は決定の経緯の記録であり、正はコードである。試作段階の ADR は後続の作業を拘束する制約ではなく、その時点の判断である。コードと ADR が食い違う場合はコードを正とする。

目的は、半年後の開発者や新規の参加者が、1つの ADR だけを読んで「何を、なぜ決めたか」を理解できることである。当時の会話や他の ADR を読まなくても理解できる状態を基準にする。

## ADR を書く条件

次の3条件がそろう決定だけを ADR にする。1つでも欠ける場合は、コミットログや PR の説明に書く。

1. 変更のコストが大きい。
2. 文脈を知らない読者には意外である。
3. 実際に代替案があり、理由をもって1つを選択した。

数値の調整 (期限、回数、閾値) は、方式の決定に付随する場合を除いて ADR にしない。

## 手順

1. `docs/adr/` の最大番号に1を加えて番号を決める。ファイル名は `NNNN-<決定を表す英語の slug>.md`。
2. [template.md](template.md) を複製し、必須の見出しを埋める。該当のない任意の見出しは削除する。
3. 下記の規則で点検する。分量が目安を超えた場合は分割を検討する。
4. `pnpm lint:ja` で校正する。

## 見出しと書く内容

| 見出し | 必須 | 書く内容 |
| --- | --- | --- |
| タイトル | 必須 | 決定を1文で書く。例: 「SUM はグループのセルを座標の小さい順に足す」。 |
| 冒頭の属性 | 必須 | 決定日、状態、関連する issue と PR。 |
| 要約 | 必須 | 1段落。「〜の状況で、〜の問題に対し、〜を採用し、〜を不採用とした。〜を達成し、〜を受け入れた。」の順で書く (Y-statement 形式)。 |
| 背景 | 必須 | 何が問題だったか。読者が知らない前提、制約、用語をここで説明する。 |
| 決定事項 | 必須 | 何を決めたか。範囲外のことも明記する。 |
| 保証する性質 | 任意 | プロトコルや状態遷移の決定で、この決定が守る不変条件。 |
| 理由 | 必須 | なぜその案を選択したか。根拠ごとに根拠の種類を付ける。 |
| 不採用の案 | 必須 | 案ごとに、内容と不採用の理由を書く。 |
| 影響 | 必須 | この決定で困難になること、受け入れたトレードオフ。 |
| 見直す条件 | 必須 | どの状態になったら、この決定を見直すか。見直す条件はここだけに書く。 |
| 検証 | 必須 | この決定を守っている試験、型、モデルのパス。読者がコードへ到達する経路である。存在しない場合は「なし」と書く。 |
| 未決事項 | 任意 | この決定が対象とする問題のうち、未解決の部分と、その issue。 |

### 冒頭の属性

- 状態は「採用」「ADR-NNNN で置き換え」「ADR-NNNN、ADR-MMMM に分割」「一部を ADR-NNNN で置き換え」のいずれかである。
- 関連は issue と PR の番号を書く。決定の議論が残っている場所を、読者が辿れるようにする。

### 根拠の種類

理由の各根拠の末尾に、次の記号を付ける。

- 【検査】: モデル検査や性質の試験で、規則を除外すると違反することを確認した。
- 【実測】: 計測の結果がある。
- 【推定】: 実測値からの計算である。
- 【未検証】: 推論だけである。

読者はこの記号で、どの規則を安全に変更できるかを判断する。

### 範囲外と未決事項の区別

- 範囲外 (決定事項に書く): この ADR が扱わない事項。別の決定の対象である。
- 未決事項: この ADR が扱う問題のうち、まだ解決していない部分。

## 規則

### 粒度と分量

- 1つの ADR に1つの決定を書く。「片方だけを覆せる」決定は別の ADR に分ける。相互に前提とし、一緒にしか変更できない決定群は1つの ADR にしてよい。
- 本文の目安は4,000字以内である。超える場合は、分割か、詳細の移動を検討する。
- 分割した ADR は、それぞれ背景に共通の前提を1段落で要約する。共通の前提が長い場合は、前提を GLOSSARY.md に移すか、前提そのものを1つの ADR にしてリンクする。

### 自己完結

- 依存する決定は1文で要約してリンクする。「ADR-0006 を参照」だけで済ませない。
- 作成されていない ADR の番号を参照しない。未決の事項は issue を参照する。
- 背景の前提には出典 (ADR、issue、PR) を書く。出典がない前提は、その旨を明記する。
- 用語は GLOSSARY.md の用語を使い、初出でリンクする。GLOSSARY.md にない用語は背景で定義する。
- 略語は初出で正式名称を書く。スレッド内の呼び名 (「方式 A」など) を書かない。他のリポジトリや過去の試作を参照する場合は、内容を本文で説明する。

### コードとの関係

- 型名、crate 名、ライブラリ名は英語のまま書く。変更されやすい関数名や行番号には依存しない。
- 暫定値や定数は方針 (例: 「前回の起動時間の2倍」) だけを書き、値はコードの定数のパスを示す。ADR に値を書くと、コードの変更で乖離する。
- 試験やモデルのパスは「検証」に書く。

### ADR に入れないもの

- 運用手順、検証の詳細な結果、ベンチマークの生データ。PR の説明、試験コード、モデルの README に置き、ADR からはリンクと要点だけを書く。
- 作業の TODO。issue にする。
- 改訂履歴。git で追跡できる。

### 文体

- 本文は「である」調。和語を避け、熟語とカタカナ語で書く。

## 決定を変更するとき

古い ADR の本文は書き換えない。当時の判断の記録だからである。

1. 新しい ADR を作り、背景に古い ADR の決定と変更の理由を書く。
2. 古い ADR は冒頭の状態だけを更新する (「ADR-NNNN で置き換え」など)。

誤字や壊れたリンクの修正は本文を直してよい。後続の ADR が古い ADR の決定に追加する場合も、古い ADR の本文には追記せず、状態に「一部を ADR-NNNN で置き換え」と書く。

既存の長い ADR を分割する場合は、分割後の ADR をそれぞれ新しい番号で作り、元の ADR の状態を「ADR-NNNN、ADR-MMMM に分割」にする。
