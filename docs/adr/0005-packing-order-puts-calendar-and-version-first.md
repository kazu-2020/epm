# 座標を詰める軸の順は、カレンダー、バージョン、その他とする

2026-11-05

## 決めたこと

column engine がセルの座標を u64 に詰めるときの軸の順(詰める順)を、ディメンションの種類で固定する。先頭にカレンダー(期間)、次にバージョンを置き、そのあとに普通のディメンションを DimensionGlobalId の小さい順に並べる。種類はディメンションの定義に持つ(`DimensionKind`)。

- 詰める順はすべてのメジャーと数式の途中の結果で同じにする。順をプランナーが式ごとやワークスペースごとに選ぶことはしない。
- SUM が座標の小さい順に足すとき(ADR 0001)の軸の順も、この詰める順とする。evaluator と oracle も同じ順で足す。
- メジャーの宣言の軸は詰める順に並べて定義する。違う順で宣言しても結果は同じだが、読むたびに座標を詰め直すので、メモリと時間が余分に要る。

## 理由

代表モデル v2 で、期間とバージョンを末尾から先頭に移して測った(2026-11-05、4コア)。全体再計算は4倍の規模(3.9億セル)で11.5秒から8.0秒になった。セル1つの編集の p99 は1倍で0.51秒から0.40秒、4倍で2.40秒から1.91秒になった。編集で再計算する範囲は「期間とバージョンが1つずつ」になることが多く、その範囲が連続した詰めた座標になって二分探索で取れる。

編集が速くなるのは2割で、この順を選んだ主な理由ではない。詰める順を今決めるのは、この順が次の3つの前提になるからである。

- 実績の取り込み(1期間 × 実績)と、実績と見込の境界の移動が、連続した範囲の差し替えになる。
- 複数サーバーに分けるときは期間で分ける。どのサーバーの範囲も連続した詰めた座標になる。
- ADR 0004 の逃げ道(先頭の軸で塊に分ける)の先頭の軸が、そのまま期間になる。

PREV(前月の値)は詰めた座標の期間の欄に1を足すだけで求まり、どの順でも並べ替えは要らない。前月の値を順に積む式(在庫の残高、累計)は、期間が先頭なら1か月分が1つの塊になり、前の塊から次の塊を作れる。期間が末尾だと、1か月分の行が全体に散らばる。

詰めた座標は保存の形そのものなので、順を変えると全メジャーの詰め直しになる。保存形式がまだ決まっていない今が、一番安く変えられる。

## 選ばなかった案

- **DimensionGlobalId の順のまま**: ディメンションを作った順で期間の位置が決まり、ふつうは期間が先頭にならない。上の3つの前提を満たせない。
- **プランナーが式やワークスペースごとに順を選ぶ**: 足し算、掛け算の突き合わせ、SUM は、両辺の詰めた座標が同じ順なので、先頭から1回読むだけで済む。順が違うと、そのたびに並べ替えが要る(並べ替えは 2026-11-03 のプロファイルで時間の4割を占めた)。統計で順を変えると、メンバーが増えるたびに全メジャーの詰め直しになる。
- **ワークスペースの設定で順を決める**: 間違えても気づきにくく、変えるたびに全メジャーの詰め直しになる。
- **バージョンを期間より先にする**: 複数サーバーには期間で分ける(予実差を計算するには、実績と予算が同じサーバーに要る)ので、期間が一番外側でないと1台の範囲が連続しない。取り込み(1期間 × 1バージョン)はどちらの順でも連続する。
- **先頭の軸でメジャーを塊に分ける(ADR 0004 の逃げ道を今作る)**: 塊の境目をまたぐ併合・SUM・保存の処理がすべて要る。v2 の詰めた座標は最大37ビットなので、まだ要らない。
- **先頭でない軸の絞り込みのために副索引を持つ**: 編集のたびに索引の保守が要り、編集の主な時間(変わったセルの記録)をさらに増やす。

## 影響

- `DimensionDefinition` に `kind` を足した。カレンダーとバージョンが1つのワークスペースに1つずつかどうかの検査は、ワークスペースを作るときに足す。
- メジャーを保存するときに、宣言の軸を詰める順に並べるかどうかは、保存の処理を作るときに決める。表に出す列の順は詰める順とは別に持てる。
- 期間を落とす SUM(全期間の合計、累計)が多いモデルでは得をしない。ただし DimensionGlobalId の順でも得をしないので、悪くはならない。
- 編集の主な時間は変わったセルを1つずつ記録する処理(1セル約0.5マイクロ秒)である。これは差分を列の形で持つ変更で別に直す。
