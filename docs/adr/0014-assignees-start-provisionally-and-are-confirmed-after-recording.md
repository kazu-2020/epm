# Assignee は期限付きで仮起動し、App server が配置表への記録の後に採用する

- Status: Accepted
- Date: 2026-11-20
- Related: #196、#197、#263

配置表へのアドレスの記録の前に App server が終了すると、起動済みの Assignee が残存する。この問題に対し、ランチャーが Assignee を期限付きで仮起動し、App server が記録の後に採用する方式を採用した。期限までに採用されない Assignee は、ランチャーが停止する。リースの定期的な更新、アイドルによる終了、ランチャーによる消費済みのエポックの記録で対応する案は不採用とした。ランチャーは PostgreSQL への接続なしで残存を回収できる。一方、残存する時間の上限と、複数ノードにした時点での残存の可能性を受け入れた。

## Context

[ADR 0012](0012-placement-table-issues-epochs-and-a-process-serves-one-epoch.md) では、[配置表](../../GLOSSARY.md)(PostgreSQL のワークスペースごとの1行)が[エポック](../../GLOSSARY.md)を発行し、1個の [Assignee](../../GLOSSARY.md) のプロセスは1個のエポックだけを処理する。App server はエポックの発行後に[ランチャー](../../GLOSSARY.md)へ起動を依頼し、準備の確認の後にアドレスを配置表に記録する。結果が不明な起動の依頼は再送しない。ランチャーは PostgreSQL と S3 に接続しない。

[ADR 0013](0013-launcher-is-a-node-process-that-runs-assignees-in-docker-containers.md) は、ランチャーをノードごとの独立したプロセスにし、Assignee を Docker のコンテナで起動し、管理の状態をコンテナに保存すると決定した。この構成では、App server の再起動で Assignee が停止しない。そのため、ADR 0012 の最初の実装で記録前の残存を回収していた、App server の再起動による全停止がなくなる。決定しない場合、記録されない Assignee がメモリを占有し続ける。issue #196 は、この回収を独自の永続的な台帳なしで実現することを求めた。

本文の用語は以下のとおりである。

- 仮起動: ランチャーが Assignee を起動し、期限を設定した状態。
- [採用](../../GLOSSARY.md): 配置表への記録の後に、App server が仮起動の Assignee を引き受けること。期限が解除される。
- 起動期限: エポックの発行から記録までに許容する時間。App server が配置表の行から計算する(ADR 0012)。
- 期限: 仮起動の Assignee を採用なしで稼働させる時間。起点はコンテナの作成時刻で、長さは App server が起動期限以上の値を指定する。起動期限内に記録できる Assignee を、記録の前に停止しないためである。
- 停止の猶予: 停止の依頼から強制終了までの時間(SIGTERM から SIGKILL まで)。
- 照合: ランチャーが Docker の全コンテナを検査し、停止すべき Assignee を停止する処理。
- 交代: App server が新規のエポックを発行し、Assignee を入れ替えること(ADR 0012)。

## Decision

各項目の末尾の記号は根拠の種類である。【検査】は Quint のモデルで規則を外すと性質に違反することを確認した項目、【未検証】は推論だけの項目である。

- **ランチャーの契約は、起動、採用、停止の3操作である**。 ADR 0012 の、稼働中のプロセスを検索する操作(`Find`)は持たない。【未検証】
  - 起動(`Start`)は、WorkspaceGlobalId、エポック、期限の長さを受け取り、Assignee を仮起動して、listen 中のアドレスとコンテナの識別子を返却する。ランチャーは期限を自分の時計だけで計測する。
  - 採用(`Confirm`)は、仮起動の Assignee を採用する。同時に、同一ワークスペースのより小さいエポックの Assignee を、同一ノードの範囲で全部停止する。採用済みの Assignee への再送も成功し、結果は同一である。対象のコンテナが稼働していない場合と、期限で停止を決定した後は失敗する。
  - 停止(`Stop`)は、指定したエポックの Assignee を、状態を問わず停止する。
  - 通信の自動再試行は、3操作のすべてで無効にする。採用は結果が同一なので、App server が明示的に再送してよい。停止は失敗しても再送しない(ADR 0012)。停止しなかった Assignee は、同一ノードでより大きいエポックが採用された時点で、採用か照合が停止する。
- **App server は、配置表へのアドレスの記録の後に採用を依頼する**。 記録と採用の間に依頼元の App server が終了した場合に備え、記録済みで未採用のアドレスへ転送する App server も、採用を依頼する。採用が失敗した場合は、記録済みの Assignee を不在と判定して交代を開始する。記録の前に採用すると、記録が失敗した場合でも、配置表の行が指示する Assignee (より小さいエポック) を採用が停止しうるからである。【未検証】
- **期限までに採用されない仮起動の Assignee は、ランチャーが停止する**。 期限の判定と採用はワークスペースごとに直列化し、停止を決定した後の採用は失敗させる。期限の超過は、ランチャーが起動時と一定の間隔で実行する照合が検出する。照合は、期限を超過した仮起動の Assignee を停止する。同一ワークスペースのノード内の採用済みの最大のエポックより、小さいエポックの Assignee も停止する。【未検証】
- **記録済みで未採用の Assignee も、期限を超過すればランチャーが停止する**。 記録と採用の間に依頼元の App server が終了し、期限までに要求がないワークスペースで発生する。ランチャーは配置表を参照しないので、記録済みかを判定できない。次の要求の採用が失敗し、App server が交代を開始して回復する。【未検証】
- **同一のエポックの起動を累計1回にする保証は、システム全体で成立させる**。 App server は起動を再送しない(ADR 0012)。通信の自動再試行と、1個の依頼からのコンテナの作成と起動の再実行を禁止する。結果が不明な起動は再実行せず、期限で回収する。ランチャーは消費済みのエポックを記録しない。再送の禁止を外すと、同一のエポックのプロセスが2個起動する。【検査】
  - ランチャーは同一のエポックのコンテナの起動を拒否する(ADR 0013)が、この拒否は削除前のコンテナにしか作用しない。削除の後に到着した依頼は拒否できないので、再送の禁止は省略できない。【未検証】
  - PostgreSQL の切り替えで同一のエポックが再発行される場合は例外である。変更ログの整合性は、フェンス(S3 の Slot への条件付きの書き込みで、プロセスの識別子を保持する)が保証する(ADR 0006、ADR 0012)。【検査】

```mermaid
stateDiagram-v2
    [*] --> 仮起動: 起動
    仮起動 --> 採用済み: 記録の後の採用
    仮起動 --> 停止: 期限の超過、停止の依頼、より大きいエポックの採用
    採用済み --> 停止: 停止の依頼、より大きいエポックの採用、照合
    停止 --> [*]
```

範囲外: 配置表、エポックの発行、準備の確認、アドレスの記録の規則(ADR 0012)。ランチャーのプロセスの構成と、状態の保存先(ADR 0013)。ほかの App server による記録の代行。複数ノード(#240)。アイドルによる終了(#237)。同一のエポックの2個目のプロセスの回収(フェンスによる自己停止に任せる)。

検証: 実装は存在しない。モデルの検査は `storage/quint/check.sh` が実行する。再送の禁止を外した `placement_start_resent` は、`epochStartsOneProcess` に違反する。切り替え時の整合性は `placement_failover` が検査する。仮起動、採用、照合のモデル化と試験は #196 で追加する。守る不変条件は次の2個である。

- 採用と、より小さいエポックの停止は、配置表の行が指示する Assignee と、採用済みの最大のエポック以上の Assignee を停止しない。期限による停止は対象外である。
- 同一のエポックのプロセスの起動は、累計1回である。

## Alternatives Considered

<details>
<summary>配置表を採用の正にし、ランチャーが期限の時点で参照する: ランチャーが PostgreSQL に接続する</summary>

採用の依頼が不要になる。しかしランチャーに PostgreSQL の認証情報が必要になり、ADR 0012 の分離に反する。

</details>

<details>
<summary>記録のたびに、記録したエポックより小さいエポックを停止する: 記録の後に要求がないワークスペースで、記録前の残存を回収できない</summary>

仮起動の期限が不要になる。しかし停止の契機が記録だけなので、App server が記録の前に終了し、その後に要求がないワークスペースでは、残存した Assignee が停止しない。

</details>

<details>
<summary>リースを定期的に更新する: App server が停止すると、全 Assignee が停止する</summary>

App server が Assignee ごとのリースを更新し、ランチャーは更新が途絶えた Assignee を停止する。App server の停止や更新の遅延が、健全な Assignee の全停止になる。ADR 0012 は時計の精度を前提にするリースを導入しないと決定している。

</details>

<details>
<summary>アイドルによる終了で回収する: 回収がアイドルの期限に依存し、10億セル級のワークスペースを対象外にする指定も必要になる</summary>

残存した Assignee は要求を受領しないので、アイドルの期限で終了する。しかし残存の回収をアイドルの期限に依存させない(#237)。読み込みに時間を要する10億セル級のワークスペースはアイドルで停止させないので、その指定も必要になる。

</details>

<details>
<summary>ランチャーが消費済みのエポックを記録する: ランチャーの再起動で記録が消失し、切り替えの例外も防止できない</summary>

遅延して到着した起動の依頼を、ランチャーが拒否できる。しかし記録はランチャーの再起動で消失し、永続化すると独自の台帳になる。PostgreSQL の切り替えによる同一のエポックの再発行も防止できない。遅延した起動は期限で回収できる。

</details>

## Consequences

- 契約の起動、採用、期限は Docker の機能でなく意味として定義したので、ほかの実行環境でも同一の規則で実装できる。
- 残存する時間の上限は、期限、照合の間隔、停止の猶予の和である。ランチャーの停止中は、復旧までの時間が加算される。
- 記録の後に採用が完了しなかったワークスペースは、期限の超過後の最初の要求で、停止からの起動になる。
- PostgreSQL の切り替えで配置表の行が以前の状態に戻ると、発行済みのエポックが再発行される。稼働中のプロセスを検索する操作がないので、この回復は、再発行したエポック1個ごとに起動期限の超過を待機する。ほかの App server による記録の代行もできない。
- 採用が停止するのは同一ノードの Assignee だけである。複数ノードでは、停止の依頼が喪失すると、採用済みの Assignee が残存する(#240)。
- 未解決: 照合の間隔は未決定である。`connectrpc` のクライアントで自動再試行を無効にできるかは未確認である(#196)。

見直す条件: 複数ノードにする時点(#240)。仮起動、採用、照合をモデルに追加して性質に違反した場合。切り替え後の回復の待機を許容できなくなった場合。ほかの App server による記録の代行が必要になった場合。
