# 検査済みの計算状態は workspace crate が所有する

2026-11-13

## 決定事項

ワークスペースの定義の検査、数式の compile、計算状態の更新を、`workspace` crate に集約する。`server` は変更ログの Slot と Commit Sequence、編集の encode と decode だけを扱う。

- **外部から受領する定義は `UncheckedWorkspace` で表現し、`Workspace::try_new` が検査する**。 検査を通過した `Workspace` だけが計算状態(`Calculated`)を生成可能である。
- **`Workspace::try_new` は以下の項目を拒否する**。 GlobalId の重複と名前の重複。参照先のメンバー数を超過する参照属性。異なるメンバー数または異なる種類のディメンションで作成した入力メジャー。compile に失敗する数式と循環する数式。
- **ディメンションとメジャーの名前は、1個の名前空間で一意とする**。 数式はディメンションとメジャーを同一の記法(`'名前'`)で参照する。
- **数式は依存順に整列して保持する**。 宣言の順序は結果に影響しない。同順位は MeasureGlobalId の昇順とする。
- **数式の途中の結果が 64 ビットに収容不可能な場合は、compile の時点で拒否する(ADR 0004)**。 軸の集合は、加算と乗算が両辺の和集合、SUM が BY の軸である。`FILTER` は値の軸、`'X'['D': 'm']` は値の軸から `D` を除外した軸である。
- **編集は `Edit` で表現し、`Calculated::apply` が入力メジャーへの反映と再計算を一括で実行する**。 入力メジャーと計算メジャーの区別は `Calculated` が保持する。

## 理由

- 以前は `server` の `Engine` が compile の手順と計算状態を保持し、同一の手順がベンチとテストの 14 ファイルに重複していた。定義の変更やメンバーの追加を実装すると、HTTP と S3 を扱う crate に計算の規則が増加する。
- 数式の順序が依存順と不一致の場合、差分再計算は更新前の値から計算し、エラーにならない。整列を型の生成時に実行すれば、後続の処理は順序を前提にできる。
- 64 ビットの超過を評価時に検出すると、編集の反映中に Assignee が停止する。compile の時点なら、定義の保存を拒否するだけで完了する。
- 同順位を GlobalId の順序に固定すると、宣言の順序に関係なく同一の計算順序になり、テストとベンチが再現可能になる。

## 不採用の案

- **`server` の `Engine` に検査を追加する**: 計算の規則が I/O の crate に残存し、シミュレーションなしでは検証不可能な範囲が拡大する。
- **`datagen` が検査済みの `Workspace` を返却する**: `column_engine` と `evaluator` のテストは、検査前の定義を加工して使用する。検査済みの型を返却すると、テストごとに検査前の型への変換が必要になる。
- **名前空間をディメンションとメジャーで分離する**: 同一の名前が数式中の位置によって別の対象を参照する。エラー(`DimensionAsValue`、`MeasureAsAxis`)の意味も曖昧になる。

## 影響

- `server` の `datagen` への通常の依存は残存する。定義を変更ログから復元する時点で dev 依存に移動する。
- 変更ログと HTTP の座標は行番号(`MemberIndex`)のままである。`MemberGlobalId` への変更は、メンバーの追加(#170)と同時に決定する。
- 定義の変更を変更ログに記録する時点で、`Edit` と並列の操作を `workspace` crate に追加する。
