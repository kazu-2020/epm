# 受け付けと反映を別の状態機械にし、検査は変更ログの中で行う

2026-11-09

## 決めたこと

担当の中で、受け付けと反映を別々の状態機械にする。どちらも、起きたこと(Event)を受け取り、次にしてほしいこと(Effect)を返す。I/O は外側の薄い層だけが行う。

- **受け付けは `change_log` の `Owner` が受け持つ**。 変更の要求を検査する関数を `Owner` に置き、重複の判定の後、batch への追加の前に呼ぶ。検査を通らなかった要求は理由をつけて返し、変更ログには入れない。検査に使う状態は、定義と受け付けた要求の数だけを持ち、受け付けた時点で進める。`Owner` は要求の中身をバイト列のまま渡し、セルの編集の形を知らない。
- **反映は `server` の状態機械が受け持つ**。 入力はコミットの列だけで、`Owner` の型に依存しない。計算中に確定したコミットはためておき、計算が終わったら全部まとめて次の計算を始める。走っている計算に途中からコミットを足さない。
- **まとめたコミットは、メジャーごとに Delta を合流させ、計算し直しを1回にする**。 各コミットは合流の前に1件ずつ検査し直す。
- **計算は Engine 専用の rayon のプールで行う**。 まとめ1つを1つのジョブとしてプールに渡す。受け付けの側は rayon を呼ばない。シミュレーションでは同じ計算をその場で呼び、仮想時間で計算中の時間を作る。
- **計算が終わるたびに、Engine を1つの値として公開する**。 再計算済み番号は Engine から取るので、番号と値が食い違わない。読み取りは「再計算済み番号が N 以上」の値を、その番号と一緒に返す。
- **受け付けたがまだ反映していない要求の数が上限を超えたら、受け付けで拒否する**。 数は検査の状態が自分で数える。PUT が終わっていない要求も数に入る。

## 理由

- 検査と計算が同じループにあると、重い計算の間は検査も S3 への PUT も ACK も止まる。1億セルの全体再計算は数秒から数十秒かかる。
- 番号を振る順を正確に知っているのは `Owner` だけである。`server` の側で順番を再現すると、重複の判定が2か所に分散する。すると、再送された要求が定義の変更のあとに検査し直され、正しいのに拒否されうる。
- 反映済みの Engine に対して検査すると、定義の変更を変更ログへ入れた時点で破綻する。たとえば、メンバーを追加するコミットの直後にそのメンバーへの編集が来ると、反映がまだなら拒否してしまう。検査は確定した順の最新に対して行う必要がある。
- PUT に失敗しても batch を捨てる経路はない(ADR 0006)。だから受け付けた時点で検査の状態を進めても、巻き戻しは要らない。
- 1件ずつ再計算すると、コミットの到着間隔が1回の計算時間より短くなったとき、遅延が際限なく増大する。まとめれば、遅延は計算およそ2回分で上限に達する。
- 番号と値を別々に公開すると、新しい番号と古い値の組を読みうる。
- 反映の入力をコミットの列だけにしておけば、読み取り専用サーバーは S3 の変更ログを追いかけてこの状態機械に渡すだけで作れる。

## 選ばなかった案

- **`spawn_blocking` や2つ目の tokio ランタイムで計算する**: OS スレッドの終わる順が seed から決まらず、シミュレーションの再現性が壊れる。
- **計算の途中でこまめに yield する**: rayon の並列処理の途中では手を離せないので、止まる時間を保証できない。
- **1件ずつ反映し、公開だけをまとめる**: どのコミットで落ちたかは分かりやすいが、上の理由で負荷が高いと遅れが伸び続ける。落ちたコミットは、合流前の検査が番号つきで特定する。
- **番号 N ちょうどの値を返す**: まとめて反映すると、再計算済み番号がちょうど N になる瞬間は存在しない場合がある。N ごとに値を残すのはメモリに見合わない。

## 影響

- `change_log` に、セルの編集を知らない検査の口が入る。Quint のモデルは変えない。拒否した要求は、受け取らなかった要求と同じに扱えるからである。
- 定義の変更を変更ログに入れるときは、その前後でまとめを区切る。合流する Delta の形が変わるからである。
- 読み手が古い Engine を持ち続けると、メモリに2世代分が残る。読み取りは呼び出しの間だけ Engine を持つ。
- この上限の値は、ベンチで測ってから決める。
