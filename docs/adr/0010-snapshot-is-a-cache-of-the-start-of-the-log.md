# snapshot は変更ログの先頭部分のキャッシュにする

2026-11-11

## 決めたこと

新しい担当は、変更ログを頭から全部読まず、最新の snapshot とその後ろのセグメントだけを読んで起動する。snapshot は変更ログの先頭部分を反映した状態のキャッシュで、正は変更ログのままにする。

- **snapshot には、入力メジャーのセル、Commit Sequence 0〜N-1 の Request ID の列、コミット N-1 を含む Slot S だけを入れる**。 定義はまだ変更ログにないので入れない。読むときに、メジャーの軸とディメンションの大きさが今の定義と合わなければ、その snapshot は使わない。
- **反映の側が、Engine を公開したあとに書く**。 前の snapshot から Slot が 256 進んでいて、前の snapshot の書き込みが終わっていれば書く。入力セルの値と N は公開した Engine から取るので、まだ反映していないコミットは入らない。
- **置き場所は `{ワークスペース}/snapshot/{N:020}/` にする**。 チャンクを先に書き、manifest を最後に If-None-Match で書く。manifest がない snapshot は書きかけとみなして使わない。412 は無視して読み直さない。
- **どの担当が書いてもよい**。 古い担当も書いてよい。
- **新しい担当は、`snapshot/` を LIST して新しい順に読む**。 manifest がない、読めない、定義と合わない snapshot は飛ばして1つ古いものを読む。使える snapshot がなければ Slot 0 から全部読む。
- **使った snapshot の Slot S に、コミット N-1 が同じ Request ID でなければ、alarm を出して止まる**。
- **snapshot は消さない**。 古い snapshot の削除は後で決める。

## 理由

- 起動の重さは GET の回数で決まる。Slot の数で間隔を決めれば、起動時に読むセグメントの数に上限が付く。コミットの数で数えると、グループコミットの大きさで GET の回数が変わる。
- 反映に届くコミットは、PUT が成功したか読み直しで確かめたものだけである。だから公開した Engine は常に確定した変更ログの先頭部分と一致し、古い担当が書いた snapshot も正しい。
- 同じ N の snapshot は同じ先頭部分から作るので、同じバイト列になる。2つの担当が同じ N に書いても、チャンクが混ざって壊れることはない。
- Slot S にコミット N-1 がなければ、「snapshot は先頭部分と一致する」前提が破れている。別の snapshot に移ると、そのバグを隠す。
- snapshot の書き込みに失敗しても、変更ログは残る。担当は続け、次の時点で書き直す。

## 選ばなかった案

- **計算中は snapshot を書かない**: コミットが途切れないと計算の合間がなく、ずっと書けない。起動時に読むセグメントの数が伸び続ける。
- **最新の snapshot を指すポインタを置く**: 書き換える対象が1つ増え、その競合を考える必要が出る。S3 の LIST は強い整合性を持つ。
- **Parquet で書く**: writer や zstd のバージョンでバイト列が変わる。2つの担当が同じ N に書くと、チャンクと manifest が混ざる。
- **Request ID を直近の分だけ持つ**: 重複排除の意味が変わる(ADR 0006)。7〜10 年で数 GB になりうるので、別に決める。

## 影響

- Quint のモデルは変えない。snapshot は `log/` に書かず、セグメントも消さないので、変更ログの性質はそのまま成り立つ。
- snapshot から起動すると、入力セルからの全体再計算と、後ろのセグメントの反映の2回の計算が要る。
- 定義が変更ログに入ったら、定義も snapshot に入れる。
