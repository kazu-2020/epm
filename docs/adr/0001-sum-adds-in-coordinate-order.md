# SUM はグループのセルを座標の小さい順に足す

2026-11-03

## 決めたこと

SUM はグループに入るセルを座標の小さい順に1つずつ足す。グループは、`BY` に並べた軸(属性による付け替えのあと)の座標が同じセルの集まりで、結果の1セルになる。`SUM('売上', BY '期間')` なら期間ごとに1グループ、`BY` のない `SUM('売上')` は全セルで1グループ。座標を比べるときの軸の順番は、詰める順とする(ADR 0005。カレンダー、バージョンのあとに、その他のディメンションを DimensionGlobalId の小さい順に並べる)。

## 理由

f64 の足し算は、足す順番で結果の末尾が変わる。順番を決めないと、同じ入力でも実行ごとに値が変わり、evaluator と oracle(DuckDB)の結果を agreement テストで完全一致として比べられない。許容付きの比較にすると、合計が 0 か 0 に近い値かで後の割り算が空になるかどうかが変わり、許容では吸収できない。

順番を決めれば、evaluator・oracle・これから作る column engine がビット単位で一致し、差分再計算の結果も全体再計算と一致させられる。

## 選ばなかった案

- 許容付きの比較(相対 1e-9): 上の割り算の問題があり、正しい実装どうしでも agreement テストが落ちる。
- 順番に左右されない正確な累積(superaccumulator): SUM の入力の多くは × や ÷ で丸めた計算メジャーの結果である。正確に加算しても値は改善せず、得られるのは順番への非依存性だけ。その代償として、グループごとに数百バイトの状態が必要になる(650万グループなら3GB 前後)。DuckDB には正確な和がないので、oracle が evaluator と同じアルゴリズムになり、agreement テストが独立でなくなる。
  - 見直す条件: 差分再計算で、直したセルの入るグループを座標順に足し直す時間が1秒を超えそうなとき。superaccumulator なら古い値を引いて新しい値を足すだけで、全体の再計算と同じ値になる。グループの数が少ない大きな SUM にだけ使う形を比べる。
- 値を固定小数点の numeric にする(整数部と小数部の桁数を決める): 加算は順番と無関係に正確になる。しかし × と ÷ の結果は毎回小数部の桁数に丸めるので、「保存値は丸めず表示で丸める」(2026-10-28 決定)と両立しない。要る小数部の桁数はメジャーによって違い、1つに決めにくい(円の金額は0桁でよいが、基準通貨をドルにすると円のレートは 0.0066… になる)。i64 では上限が小さく、i128 にすると 1セル 8バイト増え、× と ÷ も遅くなる。
- 順番は決めず、ROUND で丸める: ROUND を書かない式では値が実行ごとに変わったままで、丸めの境目(…5 の前後)では丸めた値も変わる。ROUND は Excel との互換のために別途作るもので、この決定と併用する。

## 影響

- DuckDB では `SUM(value ORDER BY 軸...)` と書く。素の `SUM` は並列に足すので実行ごとに順番が変わる。
- column engine は、メジャーの宣言の軸が詰める順と違うとき、読むときに座標を詰め直して並べ替える。
- 座標順に足しても `0.1 + 0.2 - 0.3` は 0 にならない(5.5e-17)。構成比の分母がこの値になると、空ではなく大きな値になる。足し算・引き算の結果が0に近い場合の0への補正(Excel にはそうする規則があるとされる)は、別途決める。
