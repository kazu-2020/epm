# メジャーの Packed Coordinate は64ビットに収まる範囲だけを受け入れる

2026-11-03

## 決めたこと

column engine は、メジャーのセルの座標を u64 1つにパッキングした形(Packed Coordinate)で持つ。各軸は、そのディメンションのメンバー数を表すのに要るビット数を使い、先頭の軸が上位のビットに入る。Packed Coordinate の大小は座標の順と同じになる。

1つのメジャーの軸のビット数の合計が64を超える場合は、そのメジャーを受け入れない。これを仕様上の上限とする。

- 合計は、メジャーを定義するときと、ディメンションにメンバーを足すときに検査する。超える場合は、どのメジャーが超えるかを示してエラーにする。
- ディメンションのメンバー数と、1つのメジャーの軸の数にも上限を置く。ただし、これはメモリや画面の都合の歯止めで、64ビットに収まることは合計の検査で守る。

代表モデル v2 の最大のメジャー(数量)は37ビットである。内訳は商品 1,500(11ビット)・取引先 400(9)・部門 300(9)・期間 36(6)・バージョン 3(2)。

## 理由

以前は u32 の列を軸ごとに持っていた。Packed Coordinate の採用で、代表モデル v2(約1億セル)の常駐メモリは 17.1 → 10.8B/セル、全体再計算は約13 → 6.2秒になった。Packed Coordinate の比較・併合・絞り込みが u64 1つの比較で済むためである。64ビットを超えるモデルのために別の表し方を持つと、この単純さを失う。

メンバー数と軸の数の上限だけで64ビットを保証すると、「1軸のビット数 × 軸の数 ≦ 64」が要る。5軸なら1軸4,096メンバーまでになり、数万の商品や取引先を持つモデルが入らない。実際のモデルは大きい軸が1〜2本で残りは小さいので、合計で検査すれば、収まるモデルを拒否せずに済む。

## 選ばなかった案

- **実在する組み合わせに番号を振る(辞書)**: 番号を出てきた順に振ると番号の順が座標の順でなくなり、メジャーどうしを1回なめて併合できなくなる。座標の順に振ると、新しい組み合わせのたびに後ろの番号がずれ、メジャー全体を再パッキングする。集計と絞り込みには行ごとの逆引きが要り、辞書を変更ログから同じに再現する仕様も増える。
- **超えたメジャーだけ u128 にパッキングする**: Packed Coordinate の型が2つになる。全メジャーを u128 にすると 10.8 → 18.8B/セルで、目標の15B/セルを超える。
- **超えたメジャーだけ u32 の列に戻す**: 遅くて大きい経路を、もう1つ持ち続けることになる。

## 影響

- 上限を超えるモデルが実際に出たら、先頭の軸(バージョンや期間など)でセルを塊に分け、塊の中では残りの軸だけを u64 にパッキングする形を足す。塊の番号と u64 の組の順は座標の順と同じなので、今の併合と集計の処理をそのまま使える。今はコードを書かない。
- メンバーが増えてある軸のビット数が1つ上がると、その軸を持つメジャーの Packed Coordinate はすべて再パッキングが要る。今の column engine は古いパッキング方式のメジャーを `MeasurePackingChanged` で拒否するだけで、再パッキングの処理はない。各軸に余裕のビットを持たせるか、コミットのときに再パッキングするかは未決。
- 数式の途中の結果も、軸の和集合を u64 にパッキングする。`SUM('A' * 'B', BY 'x')` のように途中の掛け算が結果より多くの軸を持つ数式は、計算時に `PackingTooWide` で失敗する場合がある。どのメジャーも64ビットに収まっていても同様である。evaluator はこの数式を計算できるので、2つの実装の結果が食い違う。数式を定義するときに途中の軸の和集合も検査するかは未決。
- テーブルは、メジャーを作らないビューとする(表示するたびに、メジャーごとにテーブルの軸へ集計して並べる)。全メジャーの軸の和集合を持つメジャーを作ると、この上限に当たりやすい。
- メンバー数と軸の数の上限の値は未決で、上限値の表で決める。
